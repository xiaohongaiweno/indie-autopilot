# Indie Builder Skills 产品审计

审计日期：2026-10-09  
审计视角：独立开发者的任务成功率、入口可发现性、职责边界、输出可执行性和跨 Skill 交接

## 结论

项目已经覆盖了独立开发者从机会发现到维护的大部分关键决策，但当前更像一套“产品管理知识目录”，还不是一组可以稳定协作的工作工具。31 个 Skill 的数量本身不是问题，问题在于：

- 入口描述大量使用宽泛的自然语言，同一个请求会命中多个 Skill；
- 多数 Skill 没有统一的输入契约、停止条件和机器可复用的输出；
- 多个 Skill 讲的是同一类决策，只是换了阶段或措辞；
- 推荐流程是线性的，容易让独立开发者误以为必须走完全套流程；
- 事实、推断、假设虽被多次强调，但没有成为每个输出的硬结构。

产品目标应从“覆盖完整生命周期”改成“每次调用只解决一个明确决策，并产出下一个决策可以直接使用的结果”。

## 高优先级问题

### P0：自动路由冲突

以下触发词会让入口竞争，降低自动选择的确定性：

| 冲突组 | 现状 | 建议的唯一归属 |
|---|---|---|
| `product-ux-conversion` / `conversion-optimization` | 两者都写“转化优化、漏斗、摩擦、CTA” | UX Skill 只负责尚无行为数据时的流程和界面设计；CRO 只负责已有基线数据的实验与判定 |
| `emerging-keyword-radar` / `seo-opportunity-research` / `content-marketing-engine` | 都涉及关键词、主题、搜索机会、内容 | Radar 只发现新信号；SEO 只评估 SERP 和页面机会；内容 Skill 只负责内容 brief 和编辑执行 |
| `indie-product-reach` / `distribution-channel-research` / `launch-campaign-planner` | 都涉及渠道和推广 | Reach 只做编排和优先级；Channel 只做渠道选择研究；Campaign 只做已选渠道的发布日程和资产 |
| `launch-readiness-qa` / `security-privacy-review` / `deployment-operations` | 都可能被“上线前检查/发布/安全”触发 | QA 只给发布决策；Security 只给风险审查；Deployment 只执行基础设施变更和恢复 |
| `customer-feedback-loop` / `support-knowledge-base` | 都处理用户问题、支持和反馈 | Feedback 负责证据归因和产品决策；KB 负责把已确认答案发布成文档 |
| `product-lifecycle-manager` / `project-retrospective` | 都可能输出下一阶段计划 | Lifecycle 决定产品方向；Retro 解释过去目标与执行差异 |

必须把这些边界写进各自的 `description` 和正文开头，不能只放在 `CATALOG.md`。路由器首先看到的是 frontmatter。

### P0：交付物不可交接

只有少数 Skill 明确要求证据或状态。统一要求每个 Skill 输出以下字段：

```text
决策/任务：
结论：
证据：事实、来源、核验日期
假设与未知：
建议动作：优先级、负责人、验收标准
状态：draft / ready / blocked / verified
交接给：Skill 名称或“无”
```

`verified` 只能在实际检查、测试或外部来源核验后使用；没有输入时必须输出 `blocked` 或 `evidence insufficient`，不能用通用建议填满结果。

### P1：内容偏手册，缺少执行决策

31 个文件普遍有“铁律、框架、工作流程”，但缺少三件真正影响结果的内容：

1. **何时不该调用**：例如没有现有转化基线时不能启动 A/B 实验。
2. **最低输入**：例如定价分析至少需要目标用户、成本底线、竞品价格来源或明确标注缺失。
3. **完成判定**：例如发布 QA 必须有通过/阻塞/有条件发布，而不是一份未勾选清单。

建议按 P0 先改造主流程 Skill：`product-validation`、`product-positioning`、`mvp-scope-planner`、`product-requirements`、`indie-tech-architecture`、`launch-readiness-qa`、`indie-product-reach`。

## 建议的产品结构

保留 31 个专业能力，但把它们收敛为三类入口：

### 决策型 Skill

输出“继续/停止/选择 A/选择 B”的决策：Radar、Validation、Positioning、MVP Scope、Architecture、Pricing、Lifecycle。

### 产出型 Skill

输出可以直接使用的资产：PRD、内容 brief、发布计划、支持文档、事件字典、部署 runbook、经验卡片。

### 诊断/审查型 Skill

输出问题、风险和修复优先级：Competitor、SEO、Indexing、UX、Security、Launch QA、Cost、Technical Debt、Retro、Skills Audit。

`indie-product-reach` 应明确为唯一的增长编排器；它可以调用专业 Skill，但不应重复定义 SEO、渠道或内容方法论。编排器的输出应是“本周期调用哪些 Skill、为什么、顺序、输入和验收标准”。

## 建议的调用规则

- 不把生命周期图当成必经流程。每次调用先回答“当前要做的一个决定是什么”。
- 同一请求最多选择一个主 Skill，其他 Skill 只能作为明确的下游交接。
- 没有数据的优化请求先转为诊断或数据采集，不直接给实验结论。
- 外部事实、价格、平台规则、竞品功能和用户原话必须带来源与核验日期。
- 每个输出必须明确 `status`，并区分 `planned`、`submitted`、`published`、`verified`。
- 涉及发布、付款、生产环境或外部发送时，输出操作步骤和确认点，不把“建议”写成“已完成”。

## 改造顺序

1. 先重写 7 个 P0 主流程 Skill 的 frontmatter、输入、输出和停止条件。
2. 再处理 6 组路由冲突，给每个 Skill 增加“不负责什么”的边界段落。
3. 把 `shared/working-standards.md` 的证据和状态字段变成所有 Skill 的强制输出契约。
4. 将 `CATALOG.md` 改成按“用户当前要做的决定”导航，并保留生命周期视图作为辅助索引。
5. 为每个 Skill 增加至少一个真实用户任务的验收案例；优先验证冲突组，而不是为每个文件增加更多理论内容。

## 暂不建议做的事

- 不要继续增加新的生命周期 Skill；当前缺口是边界和执行质量。
- 不要把所有 Skill 合并成一个“大而全”的独立开发者 Skill；这会降低专业上下文和自动路由质量。
- 不要用更多触发关键词解决误路由；应收窄描述并声明输入前提。

## 审计限制

本次审计基于 31 个 `SKILL.md`、`CATALOG.md`、`HANDOFF-MAP.md`、共享规范和静态结构检查。仓库没有 Skill 使用频率、用户满意度或真实任务产出数据，因此“实际效果”只能列为待验证项，不能假设现有 Skill 已被证明有效。

## 逐 Skill 深审

评分含义：

- **B：可作为基础使用**，主流程成立，但仍需补充专业判定或输入约束；
- **C：需要重构后才适合稳定使用**，存在明显误导、职责重叠或关键流程缺失；
- 本评分评估的是“当前文件作为 Agent 指令的专业可用性”，不是主题本身的重要性。

| Skill | 评分 | 已有价值 | 关键遗漏或风险 | 建议动作 |
|---|---:|---|---|---|
| `ai-coding-workflow` | B | 有工具选择、提示词、TDD、审查和上下文管理 | 更像通用教程；缺少任务前置检查、变更风险分级、最小验证矩阵、失败回滚和“何时不要让 AI 改代码” | 改成任务执行协议，增加输入（目标、范围、约束、测试命令）、变更记录、验证证据和回滚条件 |
| `competitor-intelligence` | B | 覆盖竞品识别、功能、价格、反馈、定位和渠道 | 没有竞争边界定义、样本选择规则、来源可靠性分级、时间快照和避免把营销声明当事实的规则 | 增加竞品纳入/排除标准、证据等级、核验日期、可比功能定义和结论置信度 |
| `content-marketing-engine` | B | 有主题集群、简报、日历、CTA、分发和迭代 | 与 SEO Skill 重叠；没有内容目标到业务指标的映射、原创证据、事实核查、更新淘汰规则和编辑资源估算 | 收窄为“内容资产生产与维护”，要求每篇内容绑定受众问题、证据、CTA、指标和复查日期 |
| `conversion-optimization` | C | 有漏斗、假设、实验、护栏指标和结果追踪 | 默认假设可以 A/B；未覆盖样本量、统计功效、实验污染、分流、停止规则、低流量替代方法；与 UX Skill 高度重叠 | 明确“已有基线数据才调用”；增加实验可行性门槛、非实验方法和统计解释，低流量优先序贯/前后对比与定性证据 |

| `distribution-channel-research` | B | 有渠道分类、评分、优先级和追踪 | 评分主观且无权重；“预期效果”容易变成编造；缺少渠道资格门槛、归因窗口、社区规则核验和实验预算 | 输出渠道假设与小实验，而非流量承诺；记录受众匹配、规则来源、投入上限、成功阈值和归因方法 |
| `emerging-keyword-radar` | B | 有来源、证据区分、七维评分和观察池 | 评分阈值缺少校准；“竞争度”方向容易误读；未定义趋势时间窗、去重、地域/语言和搜索意图样本 | 明确评分计算、数据窗口、地区、去重和阈值依据；每个词必须有可验证的下一步实验 |

| `indie-builder-memory` | B | 有经验卡、决策记录、验证、检索和更新 | 经验容易把单个项目结论泛化；缺少知识有效期、反例、来源可信度、冲突经验和检索触发规则 | 强制写适用范围、反例、置信度、复查日期和项目上下文；禁止无证据升级为通用规则 |
| `indie-product-radar` | B | 是当前最接近可执行工具的 Skill，有扫描、验证、评分、实验、失败记录 | 依赖的 references/assets/脚本未在仓库中完整呈现；评分模型和联网能力需要运行时约束；创始人匹配度可能引入主观偏差 | 补齐并验证引用资源；将来源可得性、重复信号、时间范围、地域、偏差和“无法联网时降级”写成硬规则 |

| `indie-tech-architecture` | B | 有技术选型、架构、成本、数据模型和 PoC | 推荐技术栈较泛；没有质量属性权衡、威胁/隐私约束、数据迁移、可观测性、供应商退出和容量假设 | 用 ADR 形式输出决策矩阵、约束、替代方案、PoC 成功标准、迁移路径和退出成本 |

| `launch-campaign-planner` | C | 有发布前、当天、发布后时间线和渠道资产 | 把 Product Hunt、HN、Reddit 规则写成静态常识；时间线使用太平洋时间且未要求确认；缺少发布资格、内容合规、应急响应和渠道归因 | 改成基于已选渠道和目标的 campaign brief；所有规则须实时核验，时间使用项目时区，增加预演、联系人和停止条件 |

| `product-analytics` | B | 有指标、AARRR、事件、看板、漏斗、留存和隐私 | 缺少指标字典、事件命名/版本、身份合并、时区、数据质量、采样、删除和实验分流 | 输出可实现的 tracking plan：事件 schema、owner、触发/去重、版本、质量检查、数据保留和决策用途 |

## 必须修正的专业性问题

这些不是文风偏好，而是会直接影响决策质量的规则问题：

1. 删除或改写固定数字和绝对承诺：`每周 1-2 篇`、`20% 时间还债`、`5 分钟回滚`、固定生命周期月份、固定收入天花板、固定成本/费率。
2. 删除过时或未定义的技术指标表述，例如将 FID 更新为当前 Core Web Vitals 体系，并要求注明数据来源和采集时间。
3. 将法律、合规、平台规则和价格内容改成“事实来源 + 核验日期 + 非法律意见/未知项”，不能把通用描述当成适用结论。
4. 禁止模板中的 `X`、`...` 直接成为最终答案；当信息不足时必须输出缺口和阻塞状态。
5. 将 `indie-product-radar` 中引用的 `references/`、`assets/`、`scoreboard.json` 等依赖逐一验证，确保 Skill 在干净环境中能运行。

## 质量门槛

一个 Skill 只有同时满足以下条件，才应标记为“专业可用”：

- 有清晰的唯一任务和排除边界；
- 明确最低输入，不足时能停止或降级；
- 方法包含领域特有的判定逻辑，而不只是概念清单；
- 外部事实有来源、日期和不确定性；
- 输出可以直接驱动下一步，包含状态、证据、负责人和验收标准；
- 至少通过一个真实任务案例和一个缺失输入案例；
- 依赖的 references、assets、脚本和工具在干净环境中可发现、可执行。
