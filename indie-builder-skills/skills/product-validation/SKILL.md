# 产品需求验证

验证一个产品方向是否值得投入开发时间。核心问题：痛点真实吗？有人在找解决方案吗？愿意付费吗？

## 铁律

1. **不编造用户反馈。** 没有真实用户原话就不能声称"用户需要这个"。
2. **区分信号强度。** 用户原帖 > 二手转述 > 自己的推测。
3. **验证 ≠ 确认偏见。** 主动找反面证据，不要只找支持自己想法的数据。
4. **没有验证就不开发。** 验证失败或证据不足时，建议暂缓或调整方向。
5. **付费意愿必须有证据。** 预售、等待列表、访谈中的明确承诺才算，"我觉得会买"不算。

## 验证框架

### 痛点验证
- 找到 ≥3 条独立用户原话（论坛、评论、工单、社交媒体）描述同一问题
- 用户当前如何绕过？用 Excel、脚本、多工具拼凑 = 强信号
- 问题频率：每天/每周/偶尔？频率决定付费意愿

### 替代方案验证
- 列出 3-5 个现有解决方案（含"不解决"也是一种替代）
- 它们哪里不够？用户抱怨什么？
- 是否有付费竞品？有人付费 = 需求真实的强信号

### 付费意愿验证
- 直接证据：预售、等待列表付款、访谈中"我现在就愿意付 X"
- 间接证据：竞品收入、同类产品 Acquire/Flippa 售价、付费广告存在
- 弱证据：点赞、收藏、"好主意"——这些不算付费证据

### 市场规模粗估
- 潜在用户数 × 竞品均价 × 可触达比例 ≈ 可服务市场
- 独立开发者甜蜜区：年 $50k-$200k
- < $30k/年标注"天花板过低"

## 工作流程

### 1. 明确假设
写下要验证的核心假设：
- 谁有这个问题？（目标用户）
- 问题是什么？（痛点描述）
- 为什么现有方案不够？（差异化）
- 愿意付多少钱？（定价假设）

### 2. 收集证据
逐个假设搜索和验证：
- 用户社区搜索（Reddit、HN、V2EX、知乎、行业论坛）
- 竞品定价页和收入数据
- 搜索趋势和关键词数据
- 相关产品的用户评价（找抱怨和缺失功能）

### 3. 设计验证实验
选择最轻量的验证方式：
- **落地页 + 等待列表**：测试兴趣和付费意愿
- **预售**：最强验证，用户实际付款
- **用户访谈**：5 人，找痛点频率和付费意愿
- **手动代做一单**：验证流程和可行性
- **冷邮件 10 家**：测试 B2B 需求

每个实验写明成功判据（如"5 次访谈中 ≥3 人愿意付 $X/月"）。

### 4. 做出判断
根据证据强度给出建议：
- **继续**：痛点真实 + 付费意愿成立 + 市场可触达
- **补充验证**：部分假设证据不足，需要更多实验
- **暂缓**：核心假设不成立或证据太弱
- **调整方向**：痛点成立但当前方案不可行，建议 pivot

### 5. 记录结果
无论结果如何，记录：
- 验证了哪些假设，证据是什么
- 哪些假设不成立，为什么
- 下一步建议
- 教训（交给 `indie-builder-memory`）

## 验证失败决策树

- 痛点不成立 → 放弃，回到 `indie-product-radar`
- 痛点成立但付费意愿不足 → 调整定价或功能范围，再验证
- 付费意愿成立但获客成本过高 → 调整渠道或缩小市场
- 观察池超过 30 天无新证据 → 降级归档

## 与其他 Skill 的关系

- `indie-product-radar`：发现机会 → 本 Skill 验证机会
- `competitor-intelligence`：需要深度竞品分析时调用
- `seo-opportunity-research`：验证 SEO 层面的需求证据
- `product-positioning`：验证通过后，进入定位阶段
- `indie-builder-memory`：沉淀验证经验和失败教训
