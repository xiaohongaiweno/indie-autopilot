# 产品需求文档

将 MVP 范围转化为可执行的需求。核心问题：每个功能具体做什么？用户怎么用？怎么算完成？

## 铁律

1. **需求来自验证，不来自想象。** 每个功能追溯到验证过的假设或用户反馈。
2. **具体 > 模糊。** "用户可以重置密码"胜过"用户管理功能"。
3. **验收标准必须可测试。** 能写出测试用例的需求才是好需求。
4. **不写实现细节。** 需求说"做什么"，不说"怎么做"（除非是技术约束）。
5. **需求会变化。** 记录变更原因，保持文档更新。

## 需求框架

### 用户故事格式
```
作为 [角色]
我想要 [功能]
以便 [收益]

验收标准：
- Given [前置条件]
- When [操作]
- Then [结果]
```

### 功能规格
每个功能包含：
- **描述**：一句话说明
- **用户故事**：谁用、怎么用、为什么用
- **验收标准**：具体、可测试的条件
- **边界情况**：异常输入、错误处理
- **依赖**：依赖哪些其他功能或服务
- **优先级**：P0/P1/P2

### 非功能需求
- **性能**：响应时间、并发用户数
- **安全**：认证、授权、数据保护
- **可用性**：SLA、备份、恢复
- **兼容性**：浏览器、设备、操作系统
- **可访问性**：WCAG 标准

## 工作流程

### 1. 输入收集
从其他 Skill 获取：
- `mvp-scope-planner`：MVP 功能列表
- `product-positioning`：定位和价值主张
- `product-ux-conversion`：UX 流程和转化设计
- `customer-feedback-loop`：用户反馈

### 2. 用户故事编写
对每个功能：
- 识别用户角色
- 编写用户故事
- 定义验收标准
- 标注优先级

### 3. 功能规格细化
对每个用户故事：
- 详细描述交互流程
- 列出边界情况
- 定义错误处理
- 标注依赖关系

### 4. 非功能需求
定义：
- 性能要求
- 安全要求
- 兼容性要求
- 可访问性要求

### 5. 优先级排序
- 按 MVP 范围分组
- P0 必须先做
- P1 按重要性排序
- P2 放入 backlog

### 6. 评审和确认
- 与利益相关者评审
- 确认理解一致
- 确认技术可行性
- 确认时间估算

```
- 用户故事

- 边界情况
- 优先级

### 功能 2: [名称]
...

## 非功能需求
- 性能

- 兼容性

## 依赖和约束
- 第三方服务
- 技术约束
- 时间约束

## 附录
- 术语表

```

## 需求变更管理

需求变化时：
- 记录变更原因
- 评估影响（时间、成本、范围）
- 更新文档版本
- 通知相关人员

- `mvp-scope-planner`：MVP 范围 → 本 Skill 详细需求
- `product-ux-conversion`：UX 设计指导需求
- `indie-tech-architecture`：技术约束影响需求
- `ai-coding-workflow`：需求指导开发
- `launch-readiness-qa`：验收标准指导测试

- 依赖和约束
