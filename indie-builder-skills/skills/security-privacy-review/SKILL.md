# 安全与隐私审查

审查产品的安全风险和隐私合规。核心问题：有什么安全漏洞？用户数据如何保护？是否符合法规？

## 铁律

1. **安全是底线，不是功能。** 不能因为赶进度跳过安全审查。
2. **最小权限原则。** 只访问必需的数据和权限。
3. **默认安全。** 默认配置应该是安全的，不需要用户额外设置。
4. **透明隐私。** 明确告知用户收集什么数据、如何使用。
5. **独立开发者也要合规。** GDPR、CCPA 等法规适用于所有处理用户数据的产品。

## 安全审查框架

### 认证与授权
- **认证方式**：密码、OAuth、Magic Link、2FA？
- **密码策略**：最小长度、复杂度要求、密码重置流程
- **会话管理**：Token 过期、刷新机制、登出处理
- **权限控制**：RBAC、资源级权限、API 权限
- **常见漏洞**：暴力破解、会话固定、权限提升

### 数据安全
- **传输加密**：HTTPS、TLS 版本、证书管理
- **存储加密**：敏感数据加密、密钥管理
- **数据分类**：PII、支付信息、业务数据
- **数据保留**：保留策略、删除机制
- **备份安全**：加密备份、访问控制

### 输入验证
- **SQL 注入**：参数化查询、ORM 使用
- **XSS**：输出编码、CSP 策略
- **CSRF**：Token 验证、SameSite Cookie
- **命令注入**：输入过滤、沙箱执行
- **文件上传**：类型检查、大小限制、病毒扫描

### API 安全
- **认证**：API Key、OAuth、JWT
- **限流**：Rate limiting、防刷机制
- **输入验证**：Schema 验证、类型检查
- **错误处理**：不泄露内部信息
- **CORS**：正确的跨域策略

### 第三方服务
- **依赖安全**：已知漏洞扫描
- **权限最小化**：只授予必需权限
- **数据流向**：数据发送到哪里？
- **合规性**：服务商是否合规？

## 隐私合规框架

### GDPR（欧盟用户）
- **合法性**：处理数据的法律依据（同意、合同、合法利益）
- **透明度**：隐私政策、Cookie 通知
- **数据主体权利**：访问、更正、删除、可携带
- **数据保护**：加密、匿名化、假名化
- **数据泄露**：72 小时内通知监管机构
- **DPO**：是否需要数据保护官？

### CCPA（加州用户）
- **知情权**：收集什么数据、如何使用
- **删除权**：用户可以要求删除
- **退出权**：不出售个人信息
- **不歧视**：行使权利不影响服务

### 通用隐私原则
- **隐私设计**：从设计阶段考虑隐私
- **最小收集**：只收集必需数据
- **目的限制**：只用于声明的目的
- **存储限制**：不再需要时删除
- **准确性**：保持数据准确

## 工作流程

### 1. 资产识别
- 列出所有用户数据
- 识别敏感数据（PII、支付信息）
- 绘制数据流向图
- 列出第三方服务

### 2. 威胁建模
- 识别攻击面
- 评估威胁（STRIDE 模型）
- 确定风险等级
- 优先处理高风险

### 3. 安全测试
- **自动化扫描**：依赖漏洞、代码扫描
- **手动测试**：渗透测试、逻辑漏洞
- **代码审查**：安全代码审查清单

### 4. 隐私审查
- **隐私政策**：是否完整、清晰？
- **Cookie 政策**：是否合规？
- **数据收集**：是否最小化？
- **用户权利**：是否支持访问、删除？

### 5. 修复和验证
- 修复发现的安全问题
- 验证修复效果
- 更新文档
- 通知用户（如需要）

### 6. 持续监控
- 依赖漏洞扫描
- 安全日志监控
- 定期安全审查
- 安全更新流程

## 常见安全问题

### 高优先级
- SQL 注入
- XSS（存储型、反射型）
- 认证绕过
- 敏感数据泄露
- 不安全的直接对象引用

### 中优先级
- CSRF
- 点击劫持
- 不安全的反序列化
- 日志中的敏感信息
- 弱密码策略

### 低优先级
- 信息泄露（版本号等）
- 不安全的重定向
- 缺少安全头
- Cookie 配置不当
