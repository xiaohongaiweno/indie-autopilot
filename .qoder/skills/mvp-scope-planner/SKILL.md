# MVP 范围规划

确定第一版做什么、不做什么。核心问题：验证什么假设？最少需要哪些功能？如何控制开发成本？

## 铁律

1. **MVP 是为了验证，不是为了完美。** 能验证假设就够，不要加"以后会有用"的功能。
2. **砍功能比加功能更重要。** 每个功能都有开发和维护成本。
3. **手动替代自动化。** 能用手动流程验证的，不要先做自动化。
4. **时间盒约束。** MVP 开发不超过 2-4 周（独立开发者）。
5. **明确不做什么。** 列出明确排除的功能，避免范围蔓延。

## 范围规划框架

### 假设映射
列出需要验证的核心假设，每个假设对应：
- 验证需要什么数据？
- 最少需要什么功能来收集数据？
- 能否用更轻量的方式验证？

### 功能分类
- **必须有（P0）**：没有就无法验证核心假设
- **应该有（P1）**：显著提升验证效果
- **可以有（P2）**：锦上添花，延后
- **不做（排除）**：明确排除，避免诱惑

### 手动替代方案
对每个功能问：
- 能否用现有工具替代？（Notion、Airtable、Zapier）
- 能否手动处理？（人工审核、手动邮件）
- 能否简化？（只做核心流程，跳过边缘场景）

### 技术债务预算
MVP 允许的技术妥协：
- 硬编码配置（不写配置系统）
- 单数据库（不做分库分表）
- 同步处理（不做消息队列）
- 基础错误处理（不做完整监控）
- 手动部署（不做 CI/CD）

但要明确：这些是**有意为之的妥协**，不是无意识的技术债。

## 工作流程

### 1. 明确验证目标
从 `product-validation` 或 `product-positioning` 获取：
- 核心假设是什么？
- 需要验证什么？
- 成功标准是什么？

### 2. 功能清单
列出所有"想要"的功能，然后逐个评估：
- 这个功能验证什么假设？
- 没有这个功能，还能验证吗？
- 开发成本是多少？
- 维护成本是多少？

### 3. 范围裁剪
- 保留 P0 功能
- 选择性保留 P1（不超过 3-5 个）
- 所有 P2 放入"发布后"列表
- 明确排除列表

### 4. 技术方案
- 技术栈选择（优先熟悉的）
- 架构决策（单体 vs 微服务，通常选单体）
- 第三方服务（认证、支付、邮件）
- 部署方式

### 5. 时间规划
- 开发时间盒：2-4 周
- 按周拆分任务
- 每周有可演示的进展
- 预留 buffer（通常 20%）

### 6. 发布标准
MVP 完成定义：
- 核心流程可走通
- 关键假设可验证
- 无阻塞性 bug
- 基础安全措施
- 可收集用户反馈

## 范围蔓延警告信号

- "这个功能很重要，必须加上"
- "竞品都有这个"
- "用户可能会需要"
- "以后改起来很麻烦"
- "先做了再说"

遇到这些说法，回到假设映射：这个功能验证什么假设？没有它真的不行吗？

## 与其他 Skill 的关系

- `product-validation`：验证通过 → 本 Skill 规划 MVP
- `product-requirements`：本 Skill 输出 → 详细需求文档
- `indie-tech-architecture`：技术方案选择
- `ai-coding-workflow`：开发执行
- `product-ux-conversion`：UX 和转化设计
