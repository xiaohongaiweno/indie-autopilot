# Developer vertical channels playbook

## Why developer-specific channels matter

Indie developers promoting to other developers have access to high-trust, high-signal channels that general audiences don't. Developer communities value authenticity, technical depth, and open-source contribution over marketing polish.

## Hacker News (Show HN)

### When to use
- You have a genuinely interesting technical product, tool, or project
- You can articulate the problem and solution clearly
- You're prepared for critical, technical feedback

### Show HN strategy

**Title format**: `Show HN: [Product Name] – [One-sentence description]`

**Timing**:
- Tuesday–Thursday, 8–10 AM Pacific Time tends to perform well
- Avoid weekends and holidays
- Check recent front page to avoid competing with similar posts

**Submission content**:
- First paragraph: What it does, who it's for, why you built it
- Second paragraph: Technical details, stack, interesting implementation choices
- Third paragraph: Current status, what's next, link to product/repo
- Be honest about limitations and what you're looking for (feedback, beta users, etc.)

**Engagement**:
- Respond to every substantive comment
- Answer technical questions thoroughly
- Don't be defensive about criticism
- Thank people for feedback even if it's harsh
- Update the post with edits if major issues are found

**What works**:
- Open-source projects with clear value
- Developer tools that solve real problems
- Technical deep-dives and build logs
- Honest "I built this because I was frustrated with X" stories

**What doesn't work**:
- Obvious marketing language
- Asking for upvotes or promotion
- Vague descriptions
- Ignoring criticism

### Measurement
Track: HN URL, date, points, comments, referral traffic, signups/downloads, quality of feedback, follow-up opportunities

## Dev.to / Hashnode / Medium publications

### Why these matter
- Long-tail SEO value (these domains have high authority)
- Developer audience actively searching for solutions
- Content lives for years, not days
- Builds your personal brand as a builder

### Content strategy

**What to write**:
- **Build logs**: "How I built X" — technical details, challenges, lessons learned
- **Tutorials**: Solve a real problem, use your product as part of the solution (don't make it the focus)
- **Lessons learned**: "What I learned from launching X", "Mistakes I made building Y"
- **Comparisons**: Honest technical comparisons (including when your product isn't the right fit)
- **Open-source announcements**: If you open-source part of your stack, write about it

**Structure**:
- Clear, descriptive title (include keywords naturally)
- Problem statement up front
- Code examples where relevant
- Screenshots or demos
- Link to product/repo at the end, not buried in the middle
- Tags: use relevant tags (e.g., #webdev, #opensource, #tutorial, #showdev)

**Platform-specific notes**:

**Dev.to**:
- Strong community, good for engagement
- Use the `showdev` tag for launches
- Cross-post from your blog (use canonical URLs)

**Hashnode**:
- Custom domain support (good for SEO)
- Good for longer, more technical content
- Active developer community

**Medium**:
- Larger audience but less developer-specific
- Good for broader "lessons learned" pieces
- Use publications like Better Programming, The Startup for reach

### Measurement
Track: Article URL, platform, date, views, reactions, comments, link clicks, referral traffic, signups

## GitHub README optimization

### Why it matters
- GitHub repos often rank highly in Google for "[product] github"
- README is the landing page for open-source projects
- Good READMEs get starred, shared, and contribute to credibility

### README checklist

**Above the fold** (visible without scrolling):
- Clear product name and one-sentence description
- Badges: build status, license, npm/pypi version, downloads (if relevant)
- Quick start: 3–5 lines to get running
- Screenshot or demo GIF if applicable

**Core sections**:
- **Features**: Bullet list of key capabilities
- **Installation**: Clear, copy-pasteable commands
- **Usage**: Basic example with code
- **Configuration**: If applicable
- **Contributing**: How to contribute, code of conduct
- **License**: Clear license statement
- **Roadmap**: What's coming next (optional but builds confidence)
- **Credits/Acknowledgments**: Show you're part of a community

**SEO and discoverability**:
- Include relevant keywords naturally in the description and README
- Add topics/tags to the repo
- Link to your website and documentation
- Include a `docs/` folder or link to external docs

**Trust signals**:
- Active maintenance (recent commits, responsive to issues)
- Clear license
- Contributing guidelines
- Code of conduct
- Testimonials or "used by" section if you have them

### Measurement
Track: Repo URL, stars, forks, watchers, issues, contributor count, referral traffic from GitHub

## API marketplaces

### When to use
- Your product is an API or has an API component
- You're targeting developers who integrate third-party APIs

### Platforms to consider

**RapidAPI**:
- Large marketplace for APIs
- Free tier can drive adoption
- Good for developer tools, data APIs, utility APIs

**AWS Marketplace / Azure Marketplace / GCP Marketplace**:
- If your product integrates with cloud platforms
- Enterprise credibility
- Requires more setup but higher trust

**Integration directories**:
- If you integrate with Slack, Notion, Zapier, etc., get listed in their directories
- These get high-intent traffic

### Listing optimization
- Clear description of what the API does
- Pricing: be transparent, offer free tier if possible
- Documentation: link to clear, working docs
- Code examples: copy-pasteable in multiple languages
- Use cases: concrete examples of what people build

### Measurement
Track: Platform, listing URL, installs/subscriptions, API calls, revenue (if applicable), referral traffic

## Build in Public (X/Twitter)

### Why it works
- Independent developer community is very active on X
- Authenticity and transparency build trust
- Drives early adopters and beta users
- Creates a narrative around your product

### What to share

**Build updates**:
- "Just shipped [feature] — here's what it does and why"
- Screenshots, short videos, GIFs of new features
- Metrics milestones ("Just hit 100 users!")

**Lessons learned**:
- "What I learned from my first 100 users"
- "Mistake I made and how I fixed it"
- Technical deep-dives on interesting problems

**Behind the scenes**:
- Revenue/metrics updates (if you're comfortable)
- Decision-making process ("Why I chose X over Y")
- Challenges and blockers (invites advice and support)

**Engagement**:
- Ask for feedback on specific features
- Share user testimonials (with permission)
- Celebrate user successes

### Strategy

**Frequency**: 2–5 posts per week, consistency matters more than volume

**Hashtags**: #buildinpublic #indiehacker #solopreneur #webdev (use sparingly, 1–2 per post)

**Engagement**:
- Reply to everyone who replies to you
- Follow and engage with other #buildinpublic accounts
- Share other people's work genuinely
- Don't just broadcast — have conversations

**Threads**:
- Use threads for longer stories or tutorials
- First tweet should hook: "I just spent 3 months building X. Here's what I learned 🧵"
- Each tweet should stand alone but flow as a narrative

**What doesn't work**:
- Only posting links without context
- Asking for retweets or promotion
- Being vague about what you're building
- Ignoring replies

### Measurement
Track: Follower growth, engagement rate, link clicks, referral traffic, signups from Twitter, quality of conversations

## Other developer channels to consider

**Reddit (developer subreddits)**:
- r/webdev, r/programming, r/SideProject, r/InternetIsBeautiful
- Follow each subreddit's self-promotion rules strictly
- Provide value first, link second

**Discord / Slack communities**:
- Many tech communities have dedicated channels for showcases
- Engage genuinely before promoting

**Newsletter sponsorships (barter/free)**:
- Some dev newsletters will feature your product for free if it's relevant
- Offer to write a guest post or provide exclusive discount

**Podcast guest appearances**:
- Developer podcasts are always looking for guests
- Pitch a specific topic, not just "I built a product"

## Choosing the right channels

Not every developer channel fits every product. Consider:

- **Product type**: Open-source → GitHub + Dev.to; SaaS → HN + Build in Public; API → API marketplaces + tutorials
- **Your comfort**: Don't force yourself into channels you hate
- **Audience**: Where does your target user hang out?
- **Bandwidth**: 2–3 channels done well > 10 channels done poorly

## Quality gates

- Never fabricate GitHub stars, HN upvotes, or social media engagement
- Don't cross-post the exact same content everywhere — adapt to each platform
- Disclose affiliation when posting about your product
- Provide genuine value, not just promotion
- Respect each community's rules and culture
