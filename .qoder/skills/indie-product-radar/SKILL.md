# 独立开发者产品雷达（Indie Product Radar）

核心流程：**多源信号 → 交叉验证 → 打分 → 机会卡 → 决策**。
单一信号（如某词搜索量上涨、某产品上了 Product Hunt 榜首）**不算机会**；至少 3 类信号同时出现才值得深挖。

## 铁律（先读，违反即失败）

1. **不编造数据。** 搜索量、收入、用户数、价格，找不到就写"未核实"，绝不估算后当事实写。
2. **事实与推测分开写。** 每张机会卡的备注里用【事实】【推测】【风险】三段标注；每条事实附链接。
3. **证据分级。** 来源可信度从高到低：用户原帖/评论/工单 > 官方定价页与更新日志 > 公开收入平台 > 第三方评测 > 聚合型榜单文章与卖方博客（竞品写的"替代品对比"属卖方内容，只算弱证据）。只有弱证据的维度，评分上限 5。
4. **榜单 ≠ 需求。** Product Hunt/GitHub Trending 只说明"谁在做"，不说明"谁在赚钱"，不能当付费证据。
5. **保守打分。** 多数独立产品赚不到钱，宁可低估。找不到反面证据时先怀疑自己没找够。
6. **不替用户做决定。** 输出判断依据和"需要人工确认"清单。

## 工具要求

需要联网搜索与网页抓取能力（搜索、fetch 任意一种工具即可）。若当前环境没有联网工具：明确告诉用户无法做真实扫描，只能基于用户提供的材料整理，**不要用记忆冒充实时数据**。需要 Python 3 运行 `scripts/score.py`（仅标准库，用于内部打分与校验）。

## 工作目录约定

所有状态保存在当前项目的 `radar-data/`（没有则创建）：

```
radar-data/
├── profile.md              # 用户约束与创始人背景（技术栈、投入时间、B2B/B2C、回避领域、关注赛道、行业经验、受众与分发渠道）
├── scoreboard.json         # 内部打分数据（供 score.py 打分/校验，非交付物，用户无需打开）
├── scans/
│   └── YYYY-MM-DD-report.md   # 本次扫描报告（交付物）
└── failures/
    └── YYYY-MM-DD-<opportunity-name>.md   # 被淘汰或验证失败的机会记录
```

**唯一交付物是 `scans/<date>-report.md`。** `scoreboard.json` 只是脚本的打分输入，用来让七维评分精确可复现，不作为成果交给用户，也不要求用户理解其格式。

## 运行流程

### 0. 准备
- 读 `radar-data/profile.md`。不存在时：用一次提问收集（技术栈、可投入时间、B2B/B2C、回避领域、关注赛道，如"垂直 SaaS"/"办公软件"/"开发者工具"；**以及创始人背景**：你在哪些行业有深度经验或人脉？你有哪些可触达的受众/社区/内容渠道？如博客粉丝、推特关注者、行业群等）；用户不想答就用默认值（一人开发、B2B 小微企业、回避重度合规、无特定行业优势）并写入 profile，注明"默认假设"。
- 读 `radar-data/scoreboard.json`（若存在），避免重复研究已有机会；对已有机会只做增量更新。也读最近一份 `scans/*-report.md` 了解上次结论。
- 读 `radar-data/failures/`（若存在），避免重复研究已淘汰或验证失败的机会。
- 今天的日期以系统/环境提供的为准，搜索时用真实年份，不要用训练数据里的年份。

### 1. 信号扫描（找候选，不下结论）
对六层信号各扫一遍，来源和检索套路见 `references/sources.md`（含十大类数据源清单、接入方式与优先级），搜索查询模板见 `references/search-playbook.md`（含痛点发现、商业化证据、竞品弱点、市场规模等查询模板）：
SEO/需求 · 热点/趋势 · 新兴产品 · 用户痛点 · 商业化 · 竞争格局。
- 优先找**过去 14 天**升温的主题；痛点类优先取原帖/原评论。
- 把发现聚类成 **5–8 个候选方向**，每个用一句话写成"为【谁】解决【什么问题】，替代【现有方案】"。
- 偏好"老需求 + 新技术"和"大产品的小场景"；警惕泛泛的"又一个 X 替代品"。

### 2. 逐个验证（每个候选都要做，逐个搜，不要合并查询）
- **需求/SEO**：核心词与长尾词、趋势方向、SERP 前十是否有弱站。没有 Ahrefs/Semrush 数据时，写"搜索量未核实"，仅用 Autocomplete、Trends、SERP 观察作定性判断。
- **痛点**：找 ≥2 条**独立来源**的用户原话（附链接）。同一抱怨重复出现、用户用 Excel/脚本/多工具拼凑，是强信号。
- **商业化**：3–5 个竞品的定价页；公开收入（TrustMRR、Starter Story、Indie Hackers）；是否有付费广告；是否有同类产品在 Acquire/Flippa 出售。
- **竞争**：列 3–5 个竞品及其具体弱点（评价下降、停更、涨价、缺某功能）。竞品多是好事，关键看缝隙。对 Top 3 机会做深度竞品分析（功能矩阵、定价层级、用户评价情感分析、更新频率），详见 `references/analysis-frameworks.md` 第一节。
- **市场规模粗估**：潜在用户基数 × 竞品均价 × 可触达比例 ≈ SAM。独立开发者 SAM 年 $50k–$200k 即值得做；< $30k/年标注"天花板过低"。详见 `references/scoring-rubric.md` 轻量市场规模估算章节。
- **定价策略建议**：定价模式（订阅/买断/按用量/免费增值）、价格区间、功能切分建议。详见 `references/scoring-rubric.md` 定价策略建议章节。
- **时机风险评估**：判断需求是太早、正好、太晚还是窗口期。用 Why Now 框架（技术/政策/行为/市场变化）评估，详见 `references/scoring-rubric.md` 时机风险评估章节和 `references/analysis-frameworks.md` 第五节。
- **获客路径具体化**：前 100 个用户从哪来、具体渠道和动作、获客成本粗估。详见 `references/scoring-rubric.md` 获客路径具体化章节。
- **创始人匹配度**：结合 profile 中的行业经验、受众和分发渠道，评估"为什么是你做这个"。
- **Jobs-to-Be-Done 分析**（Top 3 机会）：用 JTBD 框架深挖功能性/情感性/社会性任务、当前替代方案、切换成本，详见 `references/analysis-frameworks.md` 第六节。
- **假设映射**（Top 3 机会）：列出 3-5 个关键假设（需求/付费/获客/技术/竞争），按风险排序，设计验证方法，详见 `references/analysis-frameworks.md` 第二节。
- **事前验尸**（Top 3 机会）：假设 1 年后产品失败了，倒推 3 个最可能的原因、早期预警信号和缓解计划，详见 `references/analysis-frameworks.md` 第三节。
- **风险量化矩阵**（Top 3 机会）：将风险按概率×影响量化，标注触发指标和缓解计划，详见 `references/analysis-frameworks.md` 第四节。
- **信号衰减追踪**：判断信号是持续升温还是短期热点，评估半衰期、季节性、周期性，详见 `references/analysis-frameworks.md` 第七节。
- **技术可行性深度评估**（Top 3 机会）：评估技术栈复杂度、AI 依赖性、数据可用性、合规要求，详见 `references/analysis-frameworks.md` 第八节。
- 抓不到的信息如实记入"不确定点"，不要绕过去。

### 3. 打分
按 `references/scoring-rubric.md` 的锚点给八维打 0–10 分（含创始人匹配度 fit），写一句理由。为避免心算误差，把本轮机会写进 `radar-data/scoreboard.json`（内部格式见 `references/output-schemas.md` A 节），由脚本算总分：

```bash
python3 scripts/score.py rank radar-data/scoreboard.json
```

不要心算总分；以脚本输出为准。

### 4. 闸门（脚本会标记，你也要自查）
- 一票否决项（任一命中，状态最高到"观察池"，卡片明写）：依赖单一平台 API 且无替代；重度合规；需要冷启动双边网络；消费级低付费且无广告模式。
- 信号类型 < 3：不得标"验证中"，总分≥75 也要降级并注明"先补证据"。
- 任一维度打到 ≥7，必须能指出支撑它的具体链接。
- 分级：≥75 立即验证；60–74 观察池；<60 归档/收件箱。

### 5. 输出（只交付 Markdown 报告）
1. 校验内部打分数据：`python3 scripts/score.py validate radar-data/scoreboard.json`，修到零错误（这一步保证每个机会都有证据链接、信号类数够、状态合法）。
2. `radar-data/scans/<date>-report.md`：按 `assets/report-template.md`，含 Top 3 机会卡（模板见 `references/output-schemas.md` B 节）、**机会对比矩阵**（可行性 × 回报潜力 2×2 或加权对比表）、被淘汰方向及原因、需人工确认项、与上次扫描的对比。
3. 对话里给简短摘要：Top 机会、最大风险、下一步动作。不要把整份报告再贴一遍。

**不要把 JSON 作为交付物输出给用户**；JSON 只用于内部打分/校验。若用户明确要求 JSON，再另行导出。

### 6. 每个进入前列的机会，设计 7 天验证实验
落地页+预售/等待列表、访谈 5 人、手动代做一单、冷邮件 10 家。写明成功判据（如 "5 次访谈中 ≥3 人说愿意付 $X"）。没有真实验证，不进开发。

**验证失败后的决策树**：
- 痛点不成立 → 放弃该方向，回到信号扫描
- 痛点成立但付费意愿不足 → 调整定价或功能范围，再验证一次
- 付费意愿成立但获客成本过高 → 调整获客渠道或缩小目标市场
- 观察池机会超过 30 天无新证据 → 降级为归档

**失败记录**：验证失败或主动放弃的机会，按 `assets/failure-record-template.md` 模板记录到 `radar-data/failures/YYYY-MM-DD-<opportunity-name>.md`，写明淘汰原因、验证结果、教训和未来重评信号。这些记录供未来扫描参考，避免重复研究已失败的方向。

**校准反馈循环**：验证实验结果必须回写到 `scoreboard.json`（`validation_result` 和 `calibration_note` 字段），用于校准未来判断。详见 `references/scoring-rubric.md` 校准反馈循环章节。

## 运行模式

技能在用户**主动召唤**时运行，没有强制的每周/每日自动触发。根据用户请求选择运行模式：

- **完整扫描**（默认）：完整跑步骤 0–6，输出机会卡 + Markdown 报告，适合"帮我找产品机会"类请求。
- **快速信号收集**：只做步骤 1 的信号扫描，丢进收件箱，不打分，适合"先扫一下热点/痛点"类请求。
- **单方向深挖**：对指定赛道或产品方向做步骤 2–4 的完整验证与打分，适合"验证这个方向"类请求。
- **月度复盘**：复盘观察池，淘汰过期机会，出月度 Top 5，适合"复盘上月机会"类请求。

## 与看板配合（可选）
若用户需要把机会导入"产品雷达看板"（HTML 页面），可临时用 `scoreboard.json` 的格式导出（两者使用同一 JSON 结构）。默认不导出；仅在用户明确要 JSON 时做，并提醒看板导入会覆盖本地数据、先导出备份。
