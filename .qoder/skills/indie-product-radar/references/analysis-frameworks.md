# 深度分析框架

补充 `scoring-rubric.md` 的分析框架，用于 Top 3 机会的深度验证。

---

## 一、竞品深度分析框架

对每个进入前 3 的机会，做结构化竞品分析（不只是列 3-5 个竞品 + 弱点）：

### 1. 功能对比矩阵

列出 5-8 个关键功能，每个竞品有没有：

```
| 功能 | 我们（计划）| 竞品 A | 竞品 B | 竞品 C |
|---|---|---|---|---|
| 核心功能 1 | ✅ | ✅ | ✅ | ❌ |
| 核心功能 2 | ✅ | ❌ | ✅ | ✅ |
| 差异化功能 | ✅ | ❌ | ❌ | ❌ |
```

**判断标准**：
- 如果所有竞品都有某功能 → 这是基本要求，不是差异化
- 如果只有我们有某功能 → 这是楔子，要验证用户是否在意
- 如果所有竞品都缺某功能 → 这是市场空隙，优先验证

### 2. 定价层级分析

```
| 竞品 | 免费版 | 付费版 | 企业版 | 价格锚点 |
|---|---|---|---|---|
| A | 有（限制功能）| $29/月 | $99/月 | 中端 |
| B | 无 | $49/月 | $199/月 | 高端 |
| C | 有（限制用户数）| $9/月 | $49/月 | 低端 |
```

**判断标准**：
- 如果竞品价格差异大 → 市场分层，找你的位置
- 如果竞品价格趋同 → 市场成熟，需要差异化
- 如果竞品全免费 → 可能没有付费需求，或需要教育市场

### 3. 用户评价情感分析

从 G2/Capterra/Trustpilot 收集评价，归纳正面/负面主题：

```
竞品 A 评价分析（基于 50 条评价）：
正面主题：
- 功能强大（提及 30 次）
- 界面友好（提及 20 次）
负面主题：
- 价格太贵（提及 25 次）← 切入机会
- 客服响应慢（提及 15 次）← 切入机会
- 缺少 X 功能（提及 10 次）← 切入机会
```

**判断标准**：
- 负面主题提及 ≥10 次 = 普遍问题
- 如果多个竞品有相同负面主题 = 行业痛点
- 如果负面主题是"价格"= 可以做更便宜的替代品
- 如果负面主题是"功能缺失"= 可以做更专注的工具

### 4. 更新频率追踪

```
| 竞品 | 最近更新时间 | 过去 6 个月更新次数 | 更新方向 | 判断 |
|---|---|---|---|---|
| A | 2 周前 | 12 次 | 新功能为主 | 活跃迭代 |
| B | 3 个月前 | 2 次 | Bug 修复为主 | 可能停更 |
| C | 1 周前 | 8 次 | AI 功能为主 | 积极转型 |
```

**判断标准**：
- 更新频率 < 1 次/月 = 可能停更，用户会寻找替代品
- 更新方向与你的楔子一致 = 正面竞争，风险高
- 更新方向与你的楔子不一致 = 缝隙机会

### 5. 流量来源分析（可选，需要 SimilarWeb 等工具）

```
| 竞品 | 月访问量 | SEO 占比 | 社交占比 | 直接访问 | 判断 |
|---|---|---|---|---|---|
| A | 100k | 60% | 20% | 15% | SEO 驱动，内容营销有效 |
| B | 50k | 20% | 50% | 25% | 社交驱动，需要内容营销 |
| C | 200k | 40% | 10% | 45% | 品牌驱动，难以竞争 |
```

**判断标准**：
- 如果竞品主要靠 SEO → 你也可以通过内容营销获客
- 如果竞品主要靠社交 → 你需要建立社交渠道
- 如果竞品主要靠品牌 → 难以竞争，找其他缝隙

## 二、假设映射（Assumption Mapping）

每个机会都有隐含假设。显式列出并系统验证：

### 假设映射模板

```
机会：[机会名称]

关键假设（按风险排序）：
1. [假设 1] — 风险：高/中/低
   - 验证方法：[访谈/落地页/手动代做/冷邮件]
   - 成功判据：[如"5 次访谈中 ≥3 人确认"]
   - 如果不成立：[pivot 方向]

2. [假设 2] — 风险：高/中/低
   - 验证方法：...
   - 成功判据：...
   - 如果不成立：...

3. [假设 3] — 风险：高/中/低
   - 验证方法：...
   - 成功判据：...
   - 如果不成立：...
```

### 常见假设类型

1. **需求假设**：用户有这个痛点，且愿意寻找解决方案
2. **付费假设**：用户愿意为解决方案付费
3. **获客假设**：我们能通过 X 渠道触达目标用户
4. **技术假设**：我们能在 Y 时间内做出 MVP
5. **竞争假设**：竞品没有解决 Z 问题，用户在意 Z

### 风险等级判断

- **高风险**：如果这个假设不成立，整个方向不成立
- **中风险**：如果这个假设不成立，需要大幅调整方向
- **低风险**：如果这个假设不成立，小幅调整即可

### 验证优先级

先验证高风险假设，再验证中风险，最后验证低风险。

## 三、事前验尸（Pre-Mortem Analysis）

在验证前，假设产品失败了，倒推原因。暴露盲点。

### 事前验尸模板

```
机会：[机会名称]

假设 1 年后这个产品失败了，最可能的 3 个原因：

1. [原因 1]
   - 为什么会发生：[详细分析]
   - 早期预警信号：[什么指标说明这个风险成真]
   - 缓解计划：[如何预防]

2. [原因 2]
   - 为什么会发生：...
   - 早期预警信号：...
   - 缓解计划：...

3. [原因 3]
   - 为什么会发生：...
   - 早期预警信号：...
   - 缓解计划：...
```

### 常见失败原因

1. **需求不成立**：用户有痛点但不愿意付费
2. **获客失败**：无法触达目标用户，或获客成本过高
3. **竞争加剧**：新玩家进入，价格战
4. **技术风险**：依赖的 API/平台变化
5. **创始人倦怠**：独立开发者资源有限，难以持续
6. **时机不对**：市场太早或太晚

## 四、风险量化矩阵

将风险从文字列表升级为量化矩阵。

### 风险矩阵模板

```
| 风险 | 概率 | 影响 | 风险等级 | 缓解计划 | 触发指标 |
|---|---|---|---|---|---|
| 风险 1 | 高/中/低 | 高/中/低 | 高/中/低 | [具体动作] | [什么信号说明风险成真] |
| 风险 2 | ... | ... | ... | ... | ... |
| 风险 3 | ... | ... | ... | ... | ... |
```

### 风险等级计算

```
        影响
       低  中  高
概  低  低  低  中
率  中  低  中  高
    高  中  高  高
```

### 判断标准

- **高风险**：概率高 + 影响高 → 必须在验证前解决
- **中风险**：概率中 + 影响中 → 需要缓解计划
- **低风险**：概率低 + 影响低 → 监控即可

### 触发指标示例

- 需求风险触发：落地页转化率 < 1%
- 获客风险触发：冷邮件回复率 < 5%
- 竞争风险触发：新竞品在 3 个月内进入
- 技术风险触发：依赖的 API 涨价 > 50%

## 五、Why Now 检查

时机评估的结构化框架。判断"为什么是现在做这个"。

### Why Now 模板

```
机会：[机会名称]

为什么是现在？（至少满足 1 项）

□ 技术变化：[新 API/模型/平台让这件事变得可能]
  - 具体变化：...
  - 影响：...

□ 政策变化：[新法规让旧方案不合规]
  - 具体变化：...
  - 影响：...

□ 行为变化：[用户习惯改变了，如远程工作]
  - 具体变化：...
  - 影响：...

□ 市场变化：[某个大玩家退出/涨价/停更]
  - 具体变化：...
  - 影响：...

如果没有清晰的 Why Now → 标注"时机不明确"风险
```

### 判断标准

- 有清晰的 Why Now → 时机好，立即验证
- Why Now 不明确 → 时机风险高，需要更多证据
- Why Now 是短期热点 → 窗口期机会，需要快速行动

## 六、Jobs-to-Be-Done（JTBD）框架

深挖用户"雇佣"产品完成的任务。

### JTBD 模板

```
机会：[机会名称]

功能性任务：用户想完成什么具体工作？
- [任务 1]（如"每周生成报告"）
- [任务 2]

情感性任务：用户想避免什么负面情绪？
- [情绪 1]（如"不想加班"）
- [情绪 2]

社会性任务：用户想在同事/老板面前显得怎样？
- [形象 1]（如"显得专业"）
- [形象 2]

当前替代方案：用户现在怎么完成这个任务？
- [方案 1]（如"用 Excel 手动处理"）
- [方案 2]（如"外包给 freelancer"）

切换成本：从现有方案切换到新产品，用户要付出什么代价？
- [成本 1]（如"学习新工具的时间"）
- [成本 2]（如"迁移数据的成本"）
```

### 判断标准

- 功能性任务明确 + 当前替代方案低效 = 强信号
- 情感性任务强烈 = 用户愿意付费
- 切换成本低 = 容易获客
- 切换成本高 = 需要更强的差异化

## 七、信号衰减追踪

判断信号是持续升温还是短期热点。

### 信号衰减模板

```
信号：[信号名称]

信号半衰期：[这个热点还能持续多久？]
- AI 新闻周期：通常 2-4 周
- 产品发布热点：通常 1-2 周
- 行业趋势：通常 6-12 个月
- 技术变革：通常 2-5 年

季节性检查：[这个需求是季节性的吗？]
- 是：[如"报税工具只在 Q1 有需求"]
- 否：[如"代码审查工具全年有需求"]

周期性检查：[这个需求是周期性的吗？]
- 是：[如"电商工具在 Black Friday 前需求高"]
- 否：[如"项目管理工具全年稳定需求"]

信号趋势：
- 过去 7 天：[上升/稳定/下降]
- 过去 30 天：[上升/稳定/下降]
- 过去 12 个月：[上升/稳定/下降]
```

### 判断标准

- 信号半衰期短 + 趋势下降 = 短期热点，避开
- 信号半衰期长 + 趋势上升 = 长期机会，值得投入
- 季节性需求 = 需要规划发布时间
- 周期性需求 = 需要规划营销节奏

## 八、技术可行性深度评估

`dev` 维度的深度评估框架。

### 技术可行性模板

```
机会：[机会名称]

技术栈复杂度：
- 前端：[React/Vue/原生/无]
- 后端：[Node/Python/Go/无]
- 数据库：[PostgreSQL/MongoDB/无]
- 第三方 API：[OpenAI/Stripe/其他]
- 判断：[简单/中等/复杂]

AI 依赖性：
- 依赖 AI 模型：[是/否]
- 如果依赖：[哪个模型？GPT-4/Claude/开源？]
- 风险：[模型更新会不会破坏产品？]
- 缓解：[如何降低依赖？]

数据可用性：
- 需要训练数据：[是/否]
- 如果需要：[数据从哪来？]
- 风险：[数据获取成本、合规风险]

合规技术要求：
- 需要 SOC2：[是/否] — 成本：$X
- 需要 GDPR：[是/否] — 成本：$X
- 需要 HIPAA：[是/否] — 成本：$X
- 需要其他：...

技术风险评估：
- 风险 1：[如"依赖 OpenAI API，涨价风险"]
- 风险 2：[如"需要处理敏感数据，合规成本高"]
```

### 判断标准

- 技术栈简单 + 无 AI 依赖 + 无合规要求 = 低风险
- 技术栈复杂 + AI 依赖 + 合规要求 = 高风险，需要更多时间
- 如果技术风险过高 → 标注"技术可行性不足"，建议放弃或调整方向
